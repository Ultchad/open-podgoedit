# Model catalog

> **Status:** implemented in the web app. The catalog is factual
> interoperability data (on-wire id → name → parameter range), not vendor
> artwork, fonts or code. `apps/web/src/catalog/catalog.json` is generated by
> `tools/export_catalog.py`; `tools/validate_catalog.py` checks it against
> real preset bodies from a USB capture.

## 1. Why a catalog

The Rust core only knows what is on the wire: a block carries a numeric
`model_id` (key 25 of its model node) and a positional list of raw parameter
values. Everything a human reads — display name, category colour, parameter
name, unit, enum label, slider range — is a separate lookup table.

Keeping the table in TypeScript has two benefits:

- the dependency-free Rust core stays dependency-free;
- vendor-specific presentation can change without touching the protocol.

The same split exists in the reference implementation: `podgo-domain` behaves
like `l6helix.py`, `apps/web/src/catalog/index.ts` behaves like
`catalog.py` + `palette.py`.

## 2. Provenance

The data is derived from the MIT-licensed [openpodgo][openpodgo] project:

| Input | Contents used |
|---|---|
| `src/openpodgo/data/models.json` | model `wire_id`, `param_order`, parameter names, ranges, defaults, `value_type`, `display_type`, UI category/subcategory, `@` attributes |
| `src/openpodgo/data/controls.json` | discrete value labels (enum/boolean) referenced by `display_type` |
| `src/openpodgo/ui/palette.py` | official category colours, copied as hex values |

Those files were themselves derived by that project from the official POD Go
Edit resources and a `.pgb` backup. They are included here only as factual
interoperability information: identifiers, names, numeric ranges and colours.
No Line 6 application code, binary, font, icon or manual is redistributed.

The generated file is committed because `reverse/` is a local checkout, not a
build input of the web app.

## 3. Generation

```sh
python3 tools/export_catalog.py
# writes apps/web/src/catalog/catalog.json
```

The generated document has this shape:

```jsonc
{
  "source": { "project": "openpodgo (MIT)", "files": [...], "backup": ..., "generated_by": "tools/export_catalog.py" },
  "categories": { "Amp": "#DD1111", "Cab": "#DD1111", ... },
  "models": {
    "224": {
      "name": "HD2_VolPanVolStereo",
      "display": "Volume",
      "short": "Volume",
      "category": "Vol",
      "sub": null,
      "type": 0,
      "defaults": { "Pedal": 1.0, "VolumeTaper": false },
      "params": [
        { "n": "Pedal", "min": 0.0, "max": 1.0, "k": "cont" },
        { "n": "Level", "min": -60.0, "max": 6.0, "k": "cont" }
      ]
    }
  }
}
```

- Key = on-wire `model_id`, as stored in the preset blob.
- `n` keeps the original parameter symbol (`@` prefix included for attributes);
  the UI strips the prefix.
- `k` is the control kind: `cont` (continuous), `int` (discrete) or `bool`.
- `labels` is present only for discrete parameters whose values have official
  labels (743 of 4978 parameters).
- `category` is the UI category used for colours and the Model Select rows.
  `sub` distinguishes `Amp`/`Preamp`, `Cab`/`Legacy Cab`/`Impulse Response`.
- `type` is the JSON `@type` the vendor editor writes on the block (0 effect,
  1 amp, 2 cab, 5 delay/FX loop, …).
- `defaults` are the vendor defaults, including block attributes such as
  `@mic` and `@trails`. The offline `.pgp` editor uses them when a model is
  loaded into a block, so the result carries the same starting values POD Go
  Edit uses instead of invented ones.

Current output: **571 models**, **4978 parameters**, 743 labelled, about
443 KiB.

### Slot compatibility (offline editor)

`canSwapModel()` decides which model may load into the selected block. Effects
categories (Dist, Dyn, EQ, Mod, Delay, Reverb, Pitch, Filter) fit any Effects
block. Amp, Cab, Vol, Wah, Send/Return and Looper are single-role blocks: they
can sit in any slot, but a preset holds at most one of each, which is why an
empty slot can become a Wah or the Looper while a second amp is refused. A
Preset block keeps its role when its model is swapped, and the dedicated
Preset EQ (`HD2_EQ_STATIC_…`) only swaps for another Preset EQ. The rule comes
from the manual §5 and the reference implementation; the offline writer only
edits the JSON export, so a swap never reaches the pedal.

## 4. Runtime resolution

`apps/web/src/catalog/index.ts` exposes the catalog to React:

| Helper | Purpose |
|---|---|
| `modelById(id)` | model for a block's `modelId` |
| `modelsInCategory(c)` | sorted models of one category |
| `subcategories(c)` | ordered sub-tabs (`Amp`, `Preamp`; `Cab`, `Legacy Cab`, `Impulse Response`) |
| `categoryColor(c)` | official hex colour (`#606060` for an unknown/empty slot) |
| `tintedBackground(c)` | near-black inspector header tinted with that colour |
| `formatValue(param, value)` | display string, see §5 |
| `valueFraction(param, value)` | 0..1 slider position |
| `IO_PARAMS` | fixed Input/Output stages (not in `models.json`) |
| `processingChain`, `processingIndex` | chain helpers that skip the endpoints |
| `slotLabel(slot)` | `01A`, `01B`, … `32D` |

## 5. Value formatting

The rules mirror the reference inspector (`catalog.control_spec` +
`ParamRow`), not a guess:

1. boolean (`k == "bool"` or a JSON boolean) → the `labels` entry, else
   `On`/`Off`;
2. discrete (`k == "int"`) with labels → `labels[value - min]`, else the
   rounded integer;
3. continuous 0..1 knob → `(value * 10).toFixed(1)`, matching the pedal's
   0.0–10.0 scale (the slider end labels read `0` and `10`);
4. anything else → 4 significant digits, trailing zeros removed.

Catalog `display_type: percent` parameters are rendered `×100` by POD Go Edit,
but the POD Go hardware shows them `×10`: Classic Distortion Drive stores
`0.76` and the pedal displays `7.6`. The hardware reading is the authority, so
the same `×10` rule applies to every continuous 0..1 parameter.

The slider position is `(value - min) / (max - min)`, clamped to 0..1.
A mismatch between the catalog parameter count and the number of values stored
by the firmware is shown as a warning; the UI never silently renames values.

## 6. Validation against real presets

`tools/validate_catalog.py` reassembles every streamed object read in a
USBPcap capture and checks each `l6-helix` preset body:

- every chain `model_id` resolves to a catalog entry;
- the stored parameter count equals the catalog `param_order` length;
- the on-wire category (key 9) agrees with the catalog where both exist.

```sh
python3 tools/validate_catalog.py reverse/exports/podgo-full-backup.pcapng
```

Result on the 2026-11-12 capture (POD Go Wireless, fw 2.50 session):

```text
objects by operation: {0: 1, 1: 2, 4: 134, 254: 2, 255: 1}
presets decoded: 125, slots: 125, blocks: 1199
catalog coverage: 1199/1199 blocks matched
param-count mismatches: 3
category mismatches: 12 occurrences (3 models)
```

The 134 operation-4 reads cover 108 Factory and 26 User slots; eight User
slots are empty (`104: null`), one Factory slot (Factory slot 98) is short by
36 bytes in the capture, leaving 125 complete presets. All 1199 processing
blocks resolve to catalog models (206 distinct models).

Residual mismatches, all understood:

| Model | Catalog | Wire | Meaning |
|---|---|---|---|
| `HD2_LooperOneSwitchMono` | 10 params | 4 | Looper stores a reduced parameter set |
| `HD2_CabMicIr_4x12CaliV30` | 8 | 7 | IR cab stores one fewer value |
| `HD2_CabMicIr_4x12Greenback25` | 8 | 7 | same |
| `HD2_FXLoopMono1` | category 9 | 8 | the on-wire category is not the UI category |
| `HD2_EQ_STATIC_ParametricStereo` | 23 | 1 | `value_type`/EQ kind, not the UI category |
| `HD2_CabMicIr_4x12Greenback25` | 15 | 26 | IR cab category differs on the wire |

The lesson is that the catalog's `category` is the **UI** category used for
colours and browsing; it is not guaranteed to equal the on-wire category byte.
The validator reports both rather than treating one as wrong.

## 7. Known limitations

- The catalog is a snapshot of `openpodgo`'s data, which targets the POD Go
  model set known at the time. A future firmware can add models; an unknown id
  is shown as `Model <id>` and its parameters as `P1`, `P2`, … rather than
  hidden or mislabelled.
- Only 743 parameters have official enum labels; the rest are displayed as
  numbers even when the pedal would show a word.
- Units are not in `models.json`; the UI shows raw values and ranges. A unit
  table would need its own evidence pass. This only affects unit-bearing
  controls: delay `time_ms` values are stored in seconds on the wire and are
  therefore shown as seconds, not milliseconds, and dB/Hz parameters are shown
  as stored.
- Input/Output parameters are hard-coded from the reference (`Input Gate`,
  `Threshold`, `Decay`, `Pan`, `Level`); they have no `model_id`.
- The catalog does not make model swapping possible: only `set_param` (op 30)
  ships today, behind the gates in [writes.md](writes.md); swapping a model
  needs the chain-blob write, which is not implemented.
- The validator parses captures, not a live device. It treats `104: null` as an
  empty preset and tolerates capture-level truncation, which it reports
  indirectly as a smaller decoded count.
